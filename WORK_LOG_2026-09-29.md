## Final System Architecture

The application now preserves the architecture that was already being used by this project instead of forcing a different design from the written instructions.

### Canonical telemetry path

```text
Locust simulator
    -> MQTT publish
EMQX broker
    -> EMQX PostgreSQL rule/action
CrateDB trafostanice_sensors table
```

This remains the authoritative persistence path for telemetry.

### Realtime application path

```text
EMQX broker
    -> FastAPI MQTT subscriber
    -> normalization and latest-value cache
    -> alarm detection and persistence
    -> WebSocket broadcast
    -> Vue frontend
```

### Optional backend persistence

The backend can persist MQTT telemetry directly as a fallback, but that path is disabled by default:

```text
PERSIST_MQTT_TELEMETRY=false
```

This setting is important. Enabling both the EMQX database rule and direct backend persistence would write the same telemetry twice.

### 2. Infrastructure regression discovered

After the broader implementation, EMQX appeared to stop sending messages and CrateDB appeared to have lost its tables.

The actual failure chain was:

1. A CrateDB health check used `curl` or `wget`.
2. Those commands are not installed in the `crate:latest` image.
3. Docker therefore marked CrateDB as unhealthy even though the CrateDB process could run.
4. The backend used `depends_on` with `condition: service_healthy`.
5. The backend remained in the `Created` state and never ran database initialization.
6. EMQX continued receiving MQTT messages, but its database action failed because `trafostanice_sensors` did not exist in the newly mounted database.
7. EMQX logs reported `42P01 Relation 'trafostanice_sensors' unknown`.

At the same time, a new named Docker volume was mounted at `/data`. This did not delete the previous CrateDB data, but it hid the old anonymous volume and presented a fresh data directory. That made the existing tables and rows appear to be gone.

### 3. Infrastructure repair

The Docker configuration was corrected so that:

- Backend startup is no longer blocked by the incompatible CrateDB health check.
- CrateDB and the backend start in the correct practical order.
- The backend initializes all required tables.
- EMQX remains the canonical telemetry writer.
- Direct backend MQTT persistence is disabled by default.
- The active named CrateDB volume remains in place for stable future persistence.
- The README again documents the real EMQX rule and insert action used by this project.

### 4. Historical data recovery

The old CrateDB data was found in the anonymous Docker volume:

```text
9658437fac538b93d9a57551c5276e96be37b3974233e110cdf3ffc317aa3a76
```

It contained all seven application tables.

Before merging anything, a separate safety copy was created:

The recovery copy contained:

Historical rows were then merged into the active named volume without overwriting rows already written by the repaired system. After the initial merge, the active database contained approximately:

The telemetry count continued increasing after recovery, confirming that the live EMQX rule had resumed inserting new messages. At the final check, the telemetry table contained 10,890 rows across 1,000 distinct stations.

The temporary recovery container was removed. The recovery volume itself was deliberately preserved and should not be deleted until the active database has been independently reviewed and backed up.

### Risk-model correction

The original scoring formula treated normal raw measurements as risk contributions. A normal station at approximately 300 A and 62 C could therefore be classified as `WARNING`.

The scoring logic was corrected to measure deviation above a normal operating envelope:

- Oil temperature above 60 C.
- Current above 350 A.
- Active power above 2,600 kW.
- THD above 3 percent.
- Hydrogen above 15 ppm.

Additional penalties were added for explicit alarm states. The frontend and backend formulas were synchronized. A representative normal sample now returns `NORMAL`.

- Edge capacity.

- Estimated line loss.
- Thermal loss index.

- Overloaded-line count.

The main physics API is:

N-1 analysis now uses this physics model and returns cascade risk, estimated loss, and affected assets. Runtime verification covered a topology with 1,000 nodes and 1,149 lines.

## Simulator Changes

`locust-simulator/locustfile.py` was substantially updated.

Previously, telemetry used `publish.single`, which opened a new MQTT TCP connection for every message. It now uses one persistent Paho MQTT client per Locust user:

- Connect in `on_start`.
- Start the MQTT network loop once.
- Reuse the connection for publishes.
- Stop the loop and disconnect in `on_stop`.

This is materially more realistic and avoids unnecessary broker connection churn.

The simulator now emits low-probability advanced faults, including:

- Short circuit.
- Voltage instability.
- Frequency instability.
- Harmonics spike.
- Cooling failure.
- Insulation degradation.
- Oil leak.
- Arc discharge.
- Feeder failure.
- Transformer trip.

Measurements are adjusted to match the emitted fault flags so the alarm engine receives physically coherent samples rather than flags disconnected from the numeric data.

A controlled test with one Locust user for six seconds inserted three new CrateDB rows and stopped successfully.

## Accountability and Lessons from the Regression

I introduced the infrastructure regression by combining three changes without first validating them against the running system:

- An incompatible CrateDB health check.
- A strict backend dependency on that health status.
- A fresh named volume mounted over the existing CrateDB data path.

The result was that the backend did not initialize the schema and the previous anonymous volume was no longer mounted. EMQX still received messages but could not insert them because the new database did not contain the telemetry table.

The old data was not deleted. It was hidden by the changed mount and was subsequently recovered.

Important rules for future infrastructure work on this repository:

1. Inspect the tools actually available inside an image before adding a health-check command.
2. Inspect current container mounts and Docker volumes before changing a database volume declaration.
3. Treat a newly empty database after a mount change as a possible mount-selection problem before assuming data loss.
4. Do not replace the canonical EMQX database writer without first tracing the existing integration.
5. Do not enable both EMQX persistence and backend direct persistence without an explicit deduplication design.
6. Make a verified database export before future storage migration work.

## Known Limitations

The following items remain intentionally incomplete or suitable for a later phase:

- The grid topology and telemetry are synthetic, not utility-source data.
- AI outputs are explainable baseline calculations, not trained or calibrated production ML models.
- The physics model is simplified and is not a full AC power-flow solver.
- Some health and risk logic exists in both frontend and backend and could drift in the future.
- EMQX database-rule provisioning is manual rather than declarative.
- Metric history held by the frontend store is local to the browser session.
- The backend can perform a startup scan that may need further optimization as data volume grows.
- Full browser end-to-end tests are not automated.
- WebSocket behavior is not covered by a full automated end-to-end suite.
- The large map dependency is isolated but still produces a bundle-size warning.
- Authentication, authorization, RBAC, TLS hardening, secret management, and production network controls are not implemented.
- The system is suitable for development and demonstration, not production grid operation.
